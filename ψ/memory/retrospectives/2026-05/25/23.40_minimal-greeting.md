## Honest Feedback

This session produced no friction in the traditional sense — there was nothing to do, so nothing could go wrong. But /rrr itself had friction worth naming:

1. **Oracle root detection was wrong on first pass.** The skill's detection script checks `git rev-parse --show-toplevel` for CLAUDE.md + ψ/, but tham-oracle's ψ lives at `mission-control/tham-oracle/ψ`, not at the git root. The detection script fell back to pwd (/route/mission-control) which also had no ψ. I had to do additional discovery. This is the same root-detection friction pattern that would slow any rrr run in this repo. The skill detection logic doesn't match tham-oracle's directory layout.

2. **Session ID encoding edge case.** The ENCODED_PWD sed command in the skill template doesn't handle spaces in paths — it only replaces `/` and `.`, not spaces. The correct encoded path needed `s|[ /]|-|g`. This caused PROJECT_BASE to resolve empty on first attempt, requiring a manual fix before I could get SESSION_ID.

3. **ψ not at git root.** The ψ vault for tham-oracle is nested inside the repo (`tham-oracle/ψ`), not at the top-level oracle repo root. The skill assumes one-to-one oracle→repo mapping. This repo is a multi-oracle monorepo. Every future /rrr run in mission-control will hit the same root-detection gap unless the pattern is updated.

## Lessons Learned

**In a multi-oracle monorepo, always resolve which oracle's ψ vault to write to before starting.** The git root detection in /rrr assumes one oracle per repo. In a multi-oracle structure, derive the vault path from memory/context (e.g., "who am I?" → tham-oracle → `mission-control/tham-oracle/ψ`) rather than from filesystem detection alone.

**Log trivial sessions.** A "nothing happened" session row in session-metrics is still a data point. Gaps break pattern-detection value. Keep the discipline of running /rrr even for session-boundary housekeeping.
